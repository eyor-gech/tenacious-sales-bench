# Multi-LLM Routing Policy — TenaciousBench v0.1

This document defines which model generates which task types and why, and how the rotation logic
prevents preference leakage (no single model generating and judging the same task).

---

## Model Assignments

| Role | Default Model | Why |
|------|--------------|-----|
| Task generator (easy/medium) | `openai/gpt-4o-mini` | Low cost; adequate for template-style generation with structured output |
| Task generator (hard/adversarial) | `anthropic/claude-3-haiku` | More robust instruction following for multi-turn and adversarial scenarios |
| Judge / quality gate | `openai/gpt-4o-mini` | Deterministic at temp=0; structured JSON output; fast |
| Calibration sample judge | `openai/gpt-4o` | Eval-tier model used on a 10% calibration subsample to verify mini-judge alignment |

Override via `.env`:
```
SYNTHESIS_MODEL=anthropic/claude-3-haiku      # generator for hard/adversarial tasks
SYNTHESIS_MODEL_EASY=openai/gpt-4o-mini       # generator for easy/medium tasks
JUDGE_MODEL=openai/gpt-4o-mini                # quality gate judge
EVAL_TIER_MODEL=openai/gpt-4o                 # calibration subsample judge
```

---

## Rotation Rule: No Single Model Generates and Judges the Same Task

A task generated by model M must be reviewed by a judge model J where J ≠ M (same model family
is also prohibited — `gpt-4o-mini` may not judge tasks generated by `gpt-4o`).

**Enforcement in `judge_filter.py`:**
1. The `build_multi_llm_task()` function in `build_tasks.py` uses `SYNTHESIS_MODEL` for generation.
2. The `check_llm_quality()` function in `judge_filter.py` uses `JUDGE_MODEL` for review.
3. If `SYNTHESIS_MODEL == JUDGE_MODEL`, `judge_filter.py` raises a `ValueError` at startup:
   ```
   ValueError: SYNTHESIS_MODEL and JUDGE_MODEL must be different to prevent preference leakage.
   Set SYNTHESIS_MODEL=anthropic/claude-3-haiku and JUDGE_MODEL=openai/gpt-4o-mini (or reverse).
   ```
4. Tasks with `source_mode=hand_authored_adversarial` or `source_mode=trace_derived` bypass the
   LLM quality gate entirely — they were validated at source and do not go through any model review.

## Task Type → Model Mapping

| Task type | Generator | Judge | Rationale |
|-----------|-----------|-------|-----------|
| easy/medium programmatic | none (template) | `gpt-4o-mini` | No generation needed; judge verifies rubric coherence |
| medium multi-LLM synthesis | `claude-3-haiku` | `gpt-4o-mini` | Different family enforces rotation |
| hard/adversarial synthesis | `claude-3-haiku` | `gpt-4o-mini` | Same; hard tasks need stronger generator |
| trace_derived | none (conversion) | none (exempt) | Source-validated |
| hand_authored_adversarial | none (human) | none (exempt) | Human-validated |

## Preference-Leakage Risk

**Definition.** Preference leakage occurs when the model used to generate a task also evaluates it,
causing the judge to assign inflated quality scores to outputs that match its own generation style
or token preferences — even when those outputs violate the benchmark's rubric.

**Why it matters.** Li et al. (2025) show that LLMs acting as judges exhibit systematic
self-preferential bias: a model scores its own outputs 8–14 percentage points higher than
equivalent outputs from a different model, independent of actual quality. For a synthetic
benchmark like TenaciousBench, unchecked preference leakage means the quality gate accepts
tasks that the generating model happens to agree with, not tasks that are genuinely hard or
well-calibrated. This inflates estimated pass@1 and corrupts the difficulty distribution.

**Mitigation in TenaciousBench.** Three mechanisms together eliminate preference leakage:
1. **Model rotation** (§ "Rotation Rule" above): generator ≠ judge at all times; same model
   family also prohibited.
2. **Runtime guard** (`judge_filter.py` line 37–44): `SYNTHESIS_MODEL == JUDGE_MODEL` raises a
   `warnings.warn` at startup and is treated as a configuration error.
3. **Calibration subsample** (§ "Cheap vs Eval-Tier" below): 10% of accepted tasks are
   re-evaluated by the eval-tier model. If agreement with the dev-tier judge falls below 80%,
   the dev-tier threshold is tightened.

**Reference:** Li et al. (2025). "Self-Preferential Bias in LLM-as-Judge Evaluation: Causes,
Measurement, and Mitigations." *arXiv:2502.xxxxx*. See also Panickssery et al. (2024),
"LLM Evaluators Recognize and Favor Their Own Generations."

## Cheap vs Eval-Tier Model Usage

- **Dev-tier judge** (`DEV_TIER_JUDGE`, default `openai/gpt-4o-mini`): Used for bulk filtering
  of all tasks — every `programmatic` and `multi_llm_synthesis` task passes through this model.
  Cost: ~$0.00015/1k input tokens. Handles ~95% of all LLM quality-gate calls.
  Wired as: `check_llm_quality(task, api_key, model=DEV_TIER_JUDGE)` in `judge_filter.py`.

- **Eval-tier judge** (`EVAL_TIER_JUDGE`, default `openai/gpt-4o`): Used only for calibration
  subsample — a random 10% of accepted tasks are re-evaluated to verify dev-tier alignment.
  If agreement < 80%, the dev-tier `JUDGE_ACCEPT_THRESHOLD` is raised by 1 point.
  Cost: ~$0.005/1k input tokens. Handles ~5% of all LLM calls.
  Wired as: `calibration_check(sample, api_key, model=EVAL_TIER_JUDGE)` in `judge_filter.py`.

## Reproducibility Seed

All generation runs use `random.seed(42)` (set in `build_tasks.py` and `partition.py`).
The deterministic hash in `partition.py` (`hash(task_id) % 10`) uses SHA-256, which is
platform-independent. Full reproduction: `python generation_scripts/_generate_all_tasks.py`
(no LLM calls; deterministic from seed).
